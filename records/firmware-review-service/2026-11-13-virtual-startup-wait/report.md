# 虚拟闪存准备超时被误报为模拟器退出

S1-ADV 0.2.201-dev 和 JIGGLER 1.0 的原审核都在会话创建后约 12 秒触发应用首帧等待超时。两次快照均处于 `flashing`，应用模拟器无进程号、画面和串口。审核器将该状态写成“模拟器退出”并发起清理。虚拟闪存缓存分别在会话创建后约 22.9 秒和 34.7 秒写完，SHA-256 与组合镜像一致。设备服务随后停止会话，两份固件当时都未进入应用运行。

修复后的审核器按单调时钟等待虚拟设备进入 `running`，启动等待上限为 180 秒。应用就绪检查随后开始，仍在运行的会话即使初次应用就绪超时，也继续执行观察。准备或启动阶段达到上限、会话提前结束分别生成可重试的服务错误，并保留状态、日志和事件。会话租期为 480 秒，为启动、应用检查与观察留出时间。观察门槛为至少 60 秒。

在与审核后端使用相同设备服务、QEMU 和 ROM 的隔离实例上，从空缓存并发提交两份已保存的原 BIN。S1-ADV 虚拟闪存准备 8.14 秒，画面为首次配置页面。JIGGLER 准备 16.56 秒，进入 `running` 后首次应用就绪仍超时，审核器继续采集画面和串口。首轮两条会话均完成至少 60 秒观察。JIGGLER 串口中已有 ESP32 的 CPU1 中断看门狗 panic，原崩溃检测漏掉了该标记。补充识别后，再从空缓存复测，JIGGLER 在虚拟运行时复现 panic，审核提前结束运行观察并按虚拟设备兼容性待定报告。S1-ADV 仍到达配置界面并完成 60 秒观察。单元测试覆盖延迟启动、仍在运行时的应用就绪超时、启动阶段终止、180 秒启动预算耗尽及串口 panic。

部署后在原审核入口重跑两个快照。S1-ADV 的 Codex 和启动检查通过，运行观察为 60.073 秒，采样 13 次。JIGGLER 的 Codex 通过，串口再次出现 CPU1 中断看门狗 panic，结果为 `E_SIM_MODEL_GAP`。

S1-ADV 的 Wi-Fi 与桥接聊天未验证。JIGGLER 的 CPU1 看门狗 panic 来自虚拟设备，现有测试无法确定固件与模型各自对该崩溃的影响。应用界面及 BLE HID 行为未验证。结果范围为虚拟设备。真机与 Burner 提交均为 `NOT RUN`。公开摘要省略任务和会话标识、路径、端点及原始日志中的配置内容。

可在基础提交执行 `git apply --check` 验证补丁。运行 `python3 -m unittest discover -s tests -q` 验证回归。回滚时恢复基础提交的审核服务源码并重新加载审核进程。
