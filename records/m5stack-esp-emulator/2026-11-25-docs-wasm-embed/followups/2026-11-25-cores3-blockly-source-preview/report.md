# Official UIFlow2 generation and CoreS3 module prerequisites

Issue #255 includes two official CoreS3 examples whose documented project artifacts are Blockly `.m5f2` files. The goal was to recover their exact runnable source through the official editor and identify the corresponding simulator data paths. A separate check investigated a source mismatch in the M5Arc documentation. [Issue #255](https://github.com/m5agent/m5stack-esp-emulator/issues/255) · [UIFlow2 IDE documentation](https://docs.m5stack.com/en/uiflow2/uiflow2_layout)

## Official source generation

The tested UIFlow2 editor reported `V2.5.5`. Its published JavaScript, Blockly toolbox, language data and style assets were captured and hashed individually. The official File Operations menu imported each original `.m5f2` from the pinned SDK revision into a fresh browser context. Code was read using the official `CodeEditorService.getWorkspaceValue()` method, which calls `CodeMakerService.makeCode()`. The test instrumented one constructor with an additional binding to the existing method in a private copy of the editor bundle. Both official and instrumented bundle digests are recorded. The compiler logic and generated bytes were unmodified. A second independent browser context used only the previously verified project and editor assets and blocked all other network traffic. Its output matched the first run byte for byte. [Source and editor asset identities](evidence/source-provenance.summary.json)

Both generated programs contain `M5`, the official module import, widget initialization, setup, a loop and the `__main__` entry. Both pass Python AST parsing. The successful executions used the supported local File Operations import after dismissing first-run onboarding. ## Attachment requirements

**DualKmeter.** The generated app constructs `DualKmeterModule(address=0x11)` and updates the label only when `is_ready()` is true. The SDK uses CoreS3 MBUS I2C1, SDA GPIO12, SCL GPIO11 at 100 kHz. It reads register `0x30` for a one-byte ready status of zero, then reads signed little-endian 32-bit hundredths of a degree Celsius from register `0x00`. A useful virtual demo needs that MBUS attachment and controller-visible readiness and temperature transitions. The current browser profile has no DualKmeter attachment. [Pinned DualKmeter driver](https://github.com/m5stack/uiflow-micropython/blob/73696ca95594646f09a39e4f525b20cf5cc550e5/m5stack/libs/module/dual_kmeter.py) · [Pinned MBUS mapping](https://github.com/m5stack/uiflow-micropython/blob/73696ca95594646f09a39e4f525b20cf5cc550e5/m5stack/libs/module/mbus.py)

**ModuleLLM.** The exact generated call selects UART2, TX GPIO17 and RX GPIO18. The SDK uses 115200 baud and 8N1. The initial app state waits for ModuleLLM ping and version responses, then sends reset and starts the audio, KWS, ASR, LLM and TTS or MeloTTS preset. Its callbacks consume the ModuleLLM UART work IDs and ASR and LLM stream messages to update the shown labels. The generated app has no on-board microphone or speaker calls. The current browser profile has no compatible ModuleLLM UART peer. A future guest run should exercise that peer with declared input and real controller traffic. [Pinned ModuleLLM driver](https://github.com/m5stack/uiflow-micropython/blob/73696ca95594646f09a39e4f525b20cf5cc550e5/m5stack/libs/module/llm.py) · [ModuleLLM voice assistant documentation](https://docs.m5stack.com/en/compute/module_llm/uiflow2)

## Default browser guest controls

Both exact generated programs were uploaded through the original CoreS3 editor and run in separate default UIFlow2 v2.5.3 guests. The locked 0046 runtime was `210db550…e211` and the workbench Flash was `b9fe8334…2d49`. DualKmeter reached the original driver and returned `OSError: 259` from `module/dual_kmeter.py` in `is_ready()`. No temperature update appeared. The ModuleLLM guest showed `Wait ModuleLLM connect` and held the original ASR and LLM placeholders for the 35-second observation. Both workbench Stop actions exited QEMU normally, removed the iframe and closed all six workers. [Execution and framebuffer identities](evidence/browser-baseline.summary.json)

## Arc and Switch source mismatch

The M5Arc documentation promises a value-change event, but the exact Arc project has only an `lvgl_page` and an `lvgl_switch`; the events target the Switch `CHECKED` and `UNCHECKED` states. The Arc and Switch `.m5f2` files share SHA-256 `5527fc169d2e9e78b6ea9a4940988b34a45485ccf8ea2ceca79970e81af3d1d1`. Their shipped Python files also share SHA-256 `ddca9d31feeee60478bacacb32d35275bc110c388924146a90b175eac7b5cc2a` and instantiate `M5Switch`. The pinned examples tree supplied no alternative project with an Arc instance. [Pinned M5Arc documentation](https://github.com/m5stack/uiflow-micropython/blob/a61a29409f09f1f4bebae05e15c4bd6dcc4956b6/docs/source/m5ui/arc.rst)

The current official `V2.5.5` editor reports `Invalid block definition for type: lvgl_switch_set_bg_color_default` on the exact legacy asset. The import retained a partial graph. Its output still constructs `M5Switch` and contains no Arc event. It is diagnostic output. A corrected upstream example requires a genuine M5Arc project plus the matching Python from the official editor. [Arc evidence](evidence/arc-upstream.summary.json)

## Same-source browser guest

The shipped Python file shared by Arc and Switch was sent without code changes to the recorded CoreS3 UIFlow2 v2.5.3 browser guest on locked `0046`. It displayed an initially grey Switch. The visible-center input `(158,106)` did not toggle it in the natural input trials. The diagnostic inverse raw touch `(106,81)` toggled the actual Switch, generating the guest serial markers `switch0 checked` and `switch0 unchecked` and changing its RGB565 framebuffer grey → green → grey. The public Stop ended QEMU with exit 0, removed its iframe and closed all six observed workers. This proves the linked program behaves as a Switch through the recorded diagnostic input route. The normal touch path remains a separate issue and deserves independent acceptance. [Firmware, runtime, exact input and framebuffer receipts](evidence/same-source-switch.summary.json)

## Reproduction and validation boundary

1. Get the exact SDK project URLs and hashes from the evidence JSON. Download the official editor assets listed there and verify their bytes before reuse.
2. In a fresh UIFlow2 session, dismiss first-run onboarding, open File Operations → Import project from local file, and load the exact project. On current editor versions with Code Preview available, use that pane to read the full program.
3. For automated capture of the pinned editor build, insert the single documented binding after its exact constructor anchor in a local replay of the minified main script. Invoke that bound `getWorkspaceValue()` on the imported workspace. Confirm the actual module or widget blocks before accepting an output. Record the full compiler output SHA-256 before running syntax checks.
4. Repeat in an independent browser context with only the verified resources. Compare output bytes. For the Arc fixture, preserve the import failure and compare the source block types and constructors with the documented Arc event.
5. Put the [browser baseline harness](code/run-stock-blockly-0046.mjs) in an owned emulator `.work` lab with the exact full Code Preview outputs. Configure the paths in the harness to the pinned SDK examples, sealed site and hashed runtime assets. Run `M5_STOCK_BLOCKLY_RUN=1 node run-stock-blockly-0046.mjs dualkmeter browser-0046-stock-blockly-dualkmeter-1` and repeat for `llm` with a new output directory. The runtime uses an isolated local origin and only the enumerated official firmware assets.

The archive records only bounded evidence and digests. It omits raw editor bundles, source snapshots, generated files and browser identifiers. No device was programmed. The generation result has no rollback requirement. Browser WASM demonstration qualification is a separate execution bound to each exact source digest, firmware and attachment profile.
