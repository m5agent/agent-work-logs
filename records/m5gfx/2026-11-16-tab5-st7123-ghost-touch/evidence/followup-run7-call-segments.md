# 第二十一轮：计时边界修正、148 ms 调用的内部分段、计数读法与 65 s 定时器枚举

日期：2026-11-18。对象：[m5stack/M5GFX#418](https://github.com/m5stack/M5GFX/issues/418)，
作者 huntson 的评论（2026-11-18T01:48:36Z）。本轮无新增运行数据，全部为固定 commit 上的
源码核对与算术。

## 1. 作者修正的内容

作者说明其计时器只包 `getTouchRaw()`：起点在 `M5.update()` 返回之后、触摸锁取得之后，
终点在该调用返回之后。因此 148 ms 是触摸调用本身，而不是 `M5.update()` 的耗时。

我方上一轮把 22–170 ms 当作“事务位于 148 ms 窗口内哪个位置”的两种读法，其中把窗口的
一部分归给 `M5.update()`。该边界不存在，故撤回“22 ms 一端 ⇒ 无停顿、扰动是被调用本身”
这一支；保留“148 ms 调用期间触摸路径没有推进、其后 22 ms 的下一次读带鬼点”的事实，
以及 1.7% 展布（8 次 147.1–149.6 ms）指向定长操作、不是排队的结论。

## 2. 148.5 ms 不在总线上：三次事务与驱动自身的上界

固定 commit `28d47949bdc84f30881623476f555398e2194313`：

- `getTouchRaw()` 在同一端口上发三次独立事务：`0x0010` 读 1 B、`0x0009` 读 1 B、
  `0x0014` 读 70 B：
  [Touch_ST7123.inl:132-141](https://github.com/m5stack/M5GFX/blob/28d47949bdc84f30881623476f555398e2194313/src/lgfx/v1/platforms/esp32p4/Touch_ST7123.inl#L132-L141)。
- 每次 `transactionWriteRead()` 各自 `beginTransaction()`/`endTransaction()`：
  [common.inl:2650-2661](https://github.com/m5stack/M5GFX/blob/28d47949bdc84f30881623476f555398e2194313/src/lgfx/v1/platforms/esp32/common.inl#L2650-L2661)。
  `beginTransaction()` 在该端口的递归互斥量上 `lock()`（L2375），
  `endTransaction()` 走 `i2c_wait(port, true)`，在 STOP 完成后才 `unlock()`。
- 驱动自身的等待都是有限的：总线忙自旋上限 128 µs（L2385-2393）；SCL 被拉低看门狗为
  2^21 个源时钟（约 13 ms，L2428-2439）；单次传输的停顿上限
  `i2c_stall_limit_us = 25000`（L1776）。

算术：

| 项 | 数值 |
| --- | --- |
| 70 B 报表读线上时间（2 B 写 + restart + 70 B 读，400 kHz） | ≈ 1.6 ms |
| 两次 1 B 读 | ≈ 0.1 ms 量级 |
| 三次传输合计 | ≈ 1.7–2.3 ms，与作者“正常调用 2.18–2.30 ms”一致 |
| 三次传输若全部触到停顿上限 | ≤ 75 ms，且每次都返回错误 |
| 作者的失败读计数 | 0 |

结论：148.5 ms 的调用里约 146 ms 位于三次传输之外——第一次传输之前、两次传输之间，
或第三次之后。无论落在哪一段，都不是线上时间；且若真是总线停顿，25 ms 上限与 13 ms
看门狗会先把失败读计数打出来（该计数为 0）。

## 3. 分段测量：四个时间戳

在 `getTouchRaw()` 内取四个时间戳：入口、第 1 次传输后、第 2 次后、第 3 次后（返回前），
与调用起点一起落盘。判别：

- 146 ms 在第 1 次传输之前 → 端口互斥量等待（另一任务持有总线）或取锁后立即被抢占；
- 146 ms 落在两次传输之间 → 抢占或 ISR 占用；
- 146 ms 落在第 3 次传输内部 → 线上停顿，与驱动 13/25 ms 上界冲突，属控制器或驱动缺陷。

## 4. FreeRTOS 运行时间计数的两条读法

作者计划 2 用调用前后读运行时间计数来“直接点名 65 s 的持有者”。两点限制：

1. 不触碰 loop 的操作（如跑在另一核上的定时器）不会出现在 >20 ms 的调用日志里，
   故“该 tick 没有慢调用”不等于“该 tick 没有操作”。
2. 计数按上下文切换采样：ISR 时间记在被中断的任务头上；阻塞在端口互斥量上的任务
   增量为 0。所以增量说明“谁占用了 CPU”，不说明“谁占用了总线”。

判别规则：

- 触摸任务自身 ≈ 148 ms，而三段各 ≈ 2 ms → CPU 时间进了中断或调用内的自旋，传输无辜；
- 另一任务 ≈ 148 ms、触摸任务 ≈ 0 → 该任务抢占了 loop，或持有端口互斥量；分段位置可分流
  （第一次传输前的等待是互斥量，因为 `beginTransaction()` 在任何总线动作之前取锁；
  传输之间的空档是抢占）。

需要 `CONFIG_FREERTOS_GENERATE_RUN_TIME_STATS`；增量单位是
`CONFIG_FREERTOS_RUN_TIME_STATS_CLK` 的计数，不是 RTOS tick，分辨率要确认远小于 148 ms。
另需一个“不慢的 tick”作对照，否则无法区分常态开销与该操作。

## 5. 65 s 定时器：先枚举，再跑

`esp_timer_dump(stdout)` 在开启 `CONFIG_ESP_TIMER_PROFILING` 时打印每个已武装
esp_timer 的参数、启动/触发次数与回调耗时（ESP-IDF v5.5 文档，esp_timer “Debugging
Timers” 一节）。在第一次 loop 通过时与 9.35 s 之后各 dump 一次：若存在 65 s 周期
esp_timer，会直接显示周期与下次到期，无需等事件发生。

若 dump 中没有 65 s 量级条目，则持有者是任务循环（一次 65 000 ms 延时，或 60 s + 5 s
的组合），此时运行时间计数才是正确工具，与作者计划 2 一致。

相位的含义：两 boots 网络分别 5.36 s / 6.40 s 起来，而相位同为 9.35 s，说明锚点在
网络之前、并在第一次 loop 附近——即武装调用在作者自己的第一轮 loop 里，不在 WiFi/IDF
初始化里；这正是第一次 loop 通过时 dump 就够用的原因。

## 6. 替换运行的两个臂

作者的替换运行（关掉 keep-alive）在计时边界修正后更干净：它复现的是已被证明的那一件事
（148 ms 内没有触摸传输）。

- 臂 A：在相同 65 s 相位上插入裸 `delay(148)`，不碰触摸。鬼点照旧 → 不读的时长本身
  就是机制，修复在主机侧调度；鬼点消失 → 操作本身（而非空档）才是因素。
- 臂 B（仅当 A 为负）：把 146 ms 放进调用内部、`0x0010` 与 `0x0014` 两次传输之间。
  不读时长不变，位置改到序列中段；若此时出现点，说明中段空档会让报表表被重新上报。

样本量：8 个 episode / 56 个 tick ≈ 14%，一小时约 8–9 次；一小时一臂足够。
