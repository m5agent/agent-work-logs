# M5GFX #418：Tab5 ST7123 停止轮询后的鬼触点，代码级核对

## 现象与结论

报告者 huntson 在 M5Stack Tab5（ST7121 面板、触摸固件版本 01、M5GFX 使用的
`Touch_ST7123` 驱动）上观察到：主机停止轮询 1.3–2.5 s 后恢复，触摸控制器会在没有人
接触时上报 `valid=1` 的点，持续 1–2 次扫描，位置集中在两条长边（raw x=0 或 719），
面积/强度与真实触摸明显不同。作者已排除 I2C 读失败（失败计数 0），并实验证明在暂停
期间由另一个任务持续每 20 ms 读取可以消除鬼触点。

本次为只读代码级核对，结论是：**M5GFX 侧没有任何过滤，控制器上报什么就发布什么；
`intensity` 字节虽然读入结构体但被丢弃。** 因此 1–2 次扫描的 `valid=1` 帧会在
M5Unified 里立即成为一次按下。至于控制器为何在轮询间隙后产生这些帧，源码无法证明，
本轮也没有可用的 Tab5 硬件或虚拟 ST7123 模型，属于未确认项。

- 证据层级：`code-level verification`
- 源码版本：M5GFX `0.3.0` / master `28d47949bdc84f30881623476f555398e2194313`；
  M5Unified master `96576a14247ddc935149145aa6b51943464120f1`
- 只读核对：没有修改 M5GFX/M5Unified，没有向对方仓库推送，没有关闭 issue

## 代码事实

| 事实 | 位置 |
| --- | --- |
| `getTouchRaw()` 用三次独立 I2C 事务读 `0x0010`（adv_info）、`0x0009`（max touches）、`0x0014`（10×7 B 报表） | `Touch_ST7123.inl:132-141` |
| 报表 7 B：byte 4 = area，byte 5 = intensity；只有 area 被写入 `touch_point_t.size` | `Touch_ST7123.inl:148` |
| `touch_point_t` 只有 x/y/size/id，没有 intensity 字段 | `Touch.hpp:29-35` |
| `wakeup()`/`sleep()` 为空；驱动只读寄存器，不写扫描模式/阈值/噪声配置，也不复位芯片 | `Touch_ST7123.hpp:41-42` |
| Tab5 的 INT 是 GPIO 23，板级构造把它作为 `pin_int` 传入，但 `Touch_ST7123` 从不配置或读取它 | `esp32p4.inl:78`、`esp32p4_construct.inl:124-130`、`Touch_ST7123.inl` 全文 |
| 面板层的 `getTouch()` 只做 `getTouchRaw()` + 坐标变换，没有过滤 | `Panel_Device.inl:538-543` |
| M5Unified 首帧 `pressed` 即进入 `touch_begin`，没有去抖；`TOUCH_MIN_UPDATE_MSEC=4 ms` | `Touch_Class.inl:26,58-100`、`Touch_Class.hpp:40-41` |
| 0.2.28 的 `Touch_ST7123.cpp` 中 `getTouchRaw()` 函数体与 0.3.0 相同 | tag `0.2.28` 对照 |

补充：`0x0009` 按公开寄存器说明是“固件配置的最大同时触点数”，不是当前帧的触点数；
本机读到 10，所以驱动实际上每帧都读满 10 个槽位。三次读不是原子操作，帧边界可能落在
两次读之间，原则上可混合两帧的字段；但在完全无手指时这不能自行制造 `valid` 位。

## 主机解析复现

把 `getTouchRaw()` 的解析逻辑（结构体、循环、area→size）原样抽到主机 C++，用报告者
给出的鬼触点数值构造 10 槽报表：

```text
sizeof(touch_report_t)=7 offsetof(intensity)=5 offsetof(area)=4
driver as shipped, ghost frame: 2 point(s)
  id=0 x=0 y=635 area(size)=34
  id=1 x=719 y=633 area(size)=36
area>=30&&intensity<25 filter, same frame: 0 point(s)
real tap (area 8, intensity 45) under same filter: 1 point(s)
narrow ghost (area 1, intensity 10), driver as shipped: 1 point(s)
narrow ghost under intensity<25 rule: 0 point(s)
```

这说明：原始逻辑会把该鬼触点帧发布成两个点；area≥30 且 intensity<25 的规则能过滤该帧
并保留真实点；窄鬼点（area 1）只有 intensity 阈值能拦住。强度值在公开 API 中不可见，
因此任何强度规则只能放进驱动内部。

## 对照实现

- **M5Stack 自己的 Tab5 参考驱动**（M5Tab5-Keyboard-UserDemo `b4c3622`，
  `esp_lcd_touch_st7123.c`）：同样的三次读、同样不检查返回值的风格，`strength` 取 area，
  没有过滤；`adv_info` 做了零初始化。
- **ESPHome `st7123`**（`eebe66da6205`）：从 `0x0010` 一次读到 `0x0014 + max_touches*7`
  （74 B），避免跨帧；INT 为下降沿，空闲时保持高电平，读取报表会清除 INT；把 intensity
  作为 raw quality 上报；同样没有鬼点过滤。
- **espp `st7123touch` 1.4.2 文档**：明确 `0x0009` 为固件配置的最大同时触点数；
  并特别说明 ST7123 不应拨动 `TP_RST`，触摸引擎由显示初始化时的 `LCD_RST` 使能。

这些对照只能说明协议和 M5GFX 的行为，不能证明控制器在空闲后切换了扫描模式。

## 对报告者三个问题的回答边界

1. **是否已知固件行为**：无法从源码确认。驱动不发任何模式切换命令；如果控制器在停止
   读取后进入低功耗/空闲扫描，那是芯片固件内部行为。作者“暂停期间持续轮询可消除鬼点”
   的实验是目前最强的芯片侧证据，但本轮未复现。
2. **是否有更新触摸固件**：M5GFX 只读 `0x0000` 并打印版本，没有升级路径；公开资料没有
   触摸固件版本说明（版本 1=ST7121、3=ST7123）。此项需要 M5Stack 硬件/FAE 确认。
3. **应在驱动过滤还是修固件**：优先芯片侧修复。单台标定的阈值对轻触、手套、低温和
   面板差异有风险，通用库硬编码阈值会静默丢点。若必须先缓解，驱动内部是当前唯一位置
   （intensity 未暴露）；建议先验证“一次事务读取”和“记录鬼点时的 INT 电平”以区分
   跨帧撕裂与芯片真实上报，再决定阈值规则。

## 追加：第二轮 INT 双帧、with_coord 与协议 §6.6（2026-11-16）

### 新增数据

报告者（huntson，同一台 Tab5、触摸固件 01）补齐了上一轮建议的两项实验，并追加了
逐帧 INT 电平：

- 7 例“相邻两帧都有坐标”，两帧之间 INT 均先高后低；字节 5/7 不同，2 例相同且都在
  单事务读取模式；
- INT 周期约 8.7 ms；不读取时约 8.7 ms 自行回高，读取会提前清除；鬼点低电平宽度
  4.8–21 ms；
- burst 结束后 10/10 次（两种模式）`adv_info` 仍为 `0x08`。

原始字节与解码见 [evidence/followup-int-trace.md](evidence/followup-int-trace.md)。

### 复核结论

1. **不是重复供给，也不是跨帧撕裂**：INT 在两帧之间先高后低，说明每次读取前控制器
   都产生过新的坐标更新；三次读非原子性无法解释这些帧。字节相同的 2 例是同一静止
   伪影在相邻帧重复上报，不是同一次读取被服务两次。
2. **`with_coord` 不能作为确认是否完成的判据**：协议 §6.6c（p.18–19）写明读到最后一个
   受支持坐标寄存器时会清除该位；`0x0009` 为 10 时最后一个寄存器是 `0x0059`，而
   stock 三次读（`0x0014` 起 70 B）与单事务读（`0x0010` 起 74 B）都覆盖到 `0x0059`。
   实测 INT 被读取清除、该位却保持 1，二者不一致。可能原因是固件未清该位，或采样
   时下一帧已重新置位；现有数据无法区分，因此上一轮“若仍为 1 则确认不完整”的表述
   不再成立。
3. **鬼点几何**：两种模式都上报 `x=0` 与 `x=719` 的成对点，area 28–32、intensity
   11–13；两端 y 差 83 / 8 / 15，而上一轮 97 例表中的成对样本差 2 和 3。“单一扫描行
   被标记”只在多数帧近似成立，稳定的不变量是两端钳位 + 低 intensity，而不是同一行。
4. **INT 低电平宽度不适合做判据**：读取会提前清除 INT，未读取时约一帧自行回高，宽度
   取决于主机服务时延（该实验的轮询周期为 23 ms），与触点持续时间没有稳定关系。

### 对过滤规则的影响

报告者当前规则是“起始 intensity ≥ 23 + 任何 area ≥ 30 的点直接丢弃”。后者与上一轮
建议的 `area >= 30 && intensity < 25` 不同：

- 鬼点 intensity 为 10–14，联合条件足以拦住全部已测鬼点；单用 area 条件并不能多拦
  任何已测样本，却可能在真实按压（area 也可达 30 以上）时整帧丢点；
- M5Unified 对缺帧的处理是松开并在下一帧重新按下，等于在长按/拖动中插入一次断点；
- 报告者已移除 40 ms 最小时长规则，缺少第二道兜底，联合条件更稳妥。

### 主机侧与协议核算

- 触点块 7 B，`0x0009`=10、`max_touch_points`=10（`Touch_ST7123.hpp:49`），最后一个
  坐标寄存器为 `0x0014 + 10*7 - 1 = 0x0059`；两种读取模式都覆盖该地址。
- `getTouchRaw()` 以 `if (adv_info.with_coord)` 作为读表门控（`Touch_ST7123.inl:134`）。
  该位长期为 1 时，门控在首次触摸后不再短路，每次调用固定执行 `0x0010` + `0x0009` +
  70 B 三次事务；属于效率问题，不影响点是否有效（约 117,000 次 INT 高电平读取未出现
  有效点，说明控制器仍按帧清除各槽位 valid 位）。

### 剩余问题与边界

- 真实手指的原始报表（尤其面板两端）仍未采集：这是当前 area/intensity 阈值的标定
  依据，也是判断“真实触点是否会落在 x=0/719”的唯一直接证据，`NOT RUN`；
- 空闲 10 s 后 `0x0010` 是否回到 `0x00`（区分“上一帧状态”与“只置不清”）：`NOT RUN`；
- 第二台 Tab5、温度、轻触/手套下的误拒率：`NOT RUN`；
- 触摸固件是否在扫描恢复时产生边缘钳位坐标、是否存在可调初始化参数：需 M5Stack 确认；
- 证据等级仍为 `code-level verification` + 报告者测量；本轮无物理 Tab5，虚拟设备
  `NOT RUN`（本地 Tab5 profile 的 ST7123 触摸是固件 GDB 邮箱，没有 I2C 寄存器模型）。

## 追加：两台 Tab5 的负向复现（2026-11-16，ainyan03）

### 新增数据

另一位测试者 ainyan03 用两台 Tab5 跑 20 ms 轮询 1.2 s + 停读 2 s 的复现片段：

| 单元 | 面板 | 轮次 | 读取次数 | 出现点的帧 |
| --- | --- | --- | --- | --- |
| A | ST7121（触摸固件 01） | 1 次启动后 10 轮 + 4×12 轮 | 600 + 2880 | 0 |
| B | ST7123 | 同上 | 600 + 2880 | 0 |

- 软件：M5GFX `develop` `b48dce04`（含 #419、#420），M5Unified `develop` `e9a8e89`，
  Arduino-ESP32 3.3.12；USB-C 供电，USB-A 口不接设备；
- 未测：网络负载、多 boot 的首 12 s。

### 复核结论

1. **不是 develop 引入的修复导致的**：`b48dce04` 中 `Touch_ST7123.inl` 自 `28d4794`
   只有 #419 一处改动（失败读返回 0、缓冲区零初始化），与报告者已用的 #417 补丁行为
   相同；#420 只改 `Touch_FT5x06.inl` / `Touch_CSTxxx.inl`。该版本 `getTouchRaw()` 仍无
   area/intensity/时长过滤，仍丢弃 intensity 字节，负向结果不能由代码变化解释。
2. **统计上不足以用“样本小”解释**：报告者暂停实验为每 40 次暂停 7–8 个鬼点（约 1/5），
   按此概率 58 轮 0 鬼点约 1e-5；而按无暂停空闲速率（约 1 h 4 个）计，58 轮（约 186 s）
   期望约 0.2 个，0 正是“未触发”应有的结果。结论应表述为暂停触发在该两台上未复现，
   而不是鬼点不存在。
3. **1.2 s 观察窗不是漏检原因**：报告者测得鬼点出现在恢复轮询后 0.1–0.95 s，落在窗内。
4. **该复现缺少阳性对照**：无人触摸时 0 帧，与读取通路根本不出点（`0x0009` 读到 0、
   #419 后任意失败读返回 0、所读实例的触摸未初始化）不可区分；需每轮一次真实按压或
   20 s 长按确认 `frames > 0`。
5. **最大未测差异**：报告者的 USB-A 口接有 USB-Ethernet（74 个鬼点/20 min 出现在 2 MB
   上传期间，暂停实验时该适配器仍插着），而本次两台 USB-A 口为空；其次是多 boot 首
   12 s（报告者 8 次 boot 中 3 次出现）与单元/固件批次（B 台触摸固件版本未给出）。

## 追加：M5Unified#367 的三字节 LCD_RST 差异（2026-11-16）

### 新增数据

报告者在同一台 Tab5 上用“强制读”（跳过 `with_coord` 门控，每次必读
`0x0010` + `0x0009` + `0x0014` 起 70 B）重跑 60 轮 × 3600 次：

- develop（M5GFX `b48dce04` / M5Unified `e9a8e89`）：0 帧含 valid 位，
  `adv_info` 3600/3600 为 `0x00`，三次读失败均为 0；
- pinned（M5GFX `d91077b9` / M5Unified `8530f53`）：92 帧，分布在 46/60 轮，
  `adv_info` 3600/3600 为 `0x08`，三次读失败均为 0。

拆分与二分：M5GFX develop + M5Unified pinned = 45/60 轮有帧；两侧都 develop = 0；
M5Unified `a5285020`（#366）44/60，`24dad4ff`（#367）0/60。

### 复核结论

1. **#367 只改三个字节，且只改 P4=LCD_RST。** `IO_DIR 0x73→0x63` 把 P4 从推挽输出改为
   输入，`PULL_SEL/PULL_EN 0x04→0x14` 给 P4 使能内部上拉。驱动自身语义（`IO_DIR`
   bit=1 为输出；`pull_up` 需 `0x0D`/`0x0B` 同时置位）证实了报告者的读法；`TP_RST`
   （P5）与其余引脚两版一致。
2. **这条线上堆栈里没有第二个写入者。** M5GFX 的 Tab5 触摸描述符无 reset 引脚，面板
   描述符无 `pin_rst`（`Panel_Device::rst_control` 直接返回），`Panel_DSI::init()` 在
   `getResetDelayBeforeDpi()==0` 时连 `CMD_SWRESET` 都不发，ST7121 也未覆盖该值；
   `Touch_ST7123` 只读不写。因此 M5Unified 扩展器初始化是唯一能改变该引脚的地方，
   二分结果与引脚差异在机理上一致。
3. **`with_coord` 常置不再算“协议确认失效”。** 有 #367 的构建上该位为 `0x00`
   （3600/3600），说明正常初始化时读表会清位；`0x08` 是控制器启动状态异常的症状，
   与鬼点在同批构建上 1:1 共变，指向同一初始化差异。上一轮“两个确认信号矛盾”的表述
   就此收窄。
4. **“必要但不充分”的形态。** 目前所有出现鬼点的构建都缺 #367；但缺 #367 并不必然
   出鬼点（报告者 sketch 在 pinned 库上为 0，`adv_info` 也是 `0x00`）。这更像初始化
   边缘条件（复位释放/上电时序）而不是确定性逻辑差异。

### 机制（未证明）

- A：状态在初始化时锁存——TDDI 的触控核与显示复位共享复位域/释放时序，强驱动与仅上拉
  给出的释放边沿不同，报表状态机停在异常态；
- B：持续电气差异——反灌/漏电/电平差异，运行期改变引脚状态即可改变行为。

判别：运行期改写 `0x43` 三个字节（不重启）看 `adv_info` 与鬼点是否立即变化；若不变，
再在运行期给 LCD_RST 一个约 10 ms 低脉冲后释放，看是否能清 `0x08`。另建议在
`M5.begin()` 后对比 sketch 与自家固件的 `0x43` 寄存器快照，解释“缺 #367 仍为 0”。

### 边界与上游问题

- 证据等级仍为 `code-level verification` + 报告者硬件测量；物理 Tab5 `NOT RUN`。
  虚拟设备 `NOT RUN`：Device Service 已把 Tab5 列为 supported/creatable，但其告警仍写明
  ST7123 触摸是固件 GDB 邮箱而非 I2C 芯片模型，且无扩展器/reset 网络模型。
- 给上游：①#367 的 commit message（“应解决弱上拉”）与字节行为（改为依赖上拉）相反，
  哪种才是 Tab5 预期，是否有需要强驱动的硬件版本？合并说明提到的 `_tab5_lcd_rst_pullup`
  按版本捕获在代码中不存在，`M5Tab5`/`M5Tab5X` 一律走上拉形式。②该面板 LCD_RST 是否
  同时复位触控核，是否有最小复位低电平/释放斜率要求？
