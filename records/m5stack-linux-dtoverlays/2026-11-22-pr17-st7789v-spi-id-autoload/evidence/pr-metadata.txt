{"author":"khalifa-mnt","baseRefName":"main","body":"**Symptom**\n\nOn a Cardputer Zero running a system other than the vendor Raspberry Pi OS image, the LCD stays dark: `panel_mipi_dbi_m` is never loaded, so there is no `/dev/fb_lcd` and no console on the screen. `modprobe panel-mipi-dbi-m` by hand brings the LCD up.\n\n**Cause**\n\nThe overlay's LCD node (`modules/CardputerZero/cardputerzero-v5-overlay.dts`, also v3) is:\n\n```dts\ncompatible = \"cardputerzero,st7789v_lcd\", \"panel-mipi-dbi-m5stack\";\n```\n\nFor a device-tree SPI device, the kernel's SPI core announces only `spi:` + the first compatible without its vendor prefix, and no `of:` modalias:\n\n```\n$ grep -h st7789v /sys/bus/spi/devices/*/modalias\nspi:st7789v_lcd\n```\n\nThe driver (`modules/st7789v-1.0/panel-mipi-dbi-m.c`) declares `spi:panel-mipi-dbi-spi` and `spi:panel-mipi-dbi-m5stack` in its SPI id table, but not `st7789v_lcd`, so udev finds no module for the device. Raspberry Pi OS hides this: `raspberrypi-sys-mods` ships `15-i2c-modprobe.rules`, which runs `i2cprobe` to retry `modprobe spi:\u003ceach compatible\u003e`. Other distributions do not have that helper.\n\nThe compatible order in the overlay cannot simply be swapped: the driver loads its init sequence from `\u003cfirst compatible\u003e.bin` (`cardputerzero,st7789v_lcd.bin`), so `cardputerzero,st7789v_lcd` has to stay first.\n\n**Fix**\n\nAdd the panel's name to the SPI id table (`modules/st7789v-1.0/panel-mipi-dbi-m.c`), so that udev loads the module for `spi:st7789v_lcd`.\n\nTested on a Cardputer Zero: with this change and no other workaround (no modprobe alias, no i2cprobe), `panel_mipi_dbi_m` loads at boot and the LCD comes up with the console.\n","createdAt":"2026-11-22T22:36:38Z","headRefName":"fix/st7789v-lcd-spi-id","isDraft":false,"mergeable":"MERGEABLE","number":17,"state":"OPEN","title":"st7789v: autoload the LCD driver on the Cardputer Zero","updatedAt":"2026-11-22T22:36:38Z","url":"https://github.com/m5stack/m5stack-linux-dtoverlays/pull/17"}
