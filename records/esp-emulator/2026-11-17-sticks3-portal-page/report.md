# Reproduction and controls

A fixed open fixture peer originally selected only the SDK SSID. On the same original release and new QEMU, the SDK selection still observed the original's beacons without accepting an association. The new opt-in profile `sticks3-open-softap-portal` selects the exact original open SSID and uses an existing local Ethernet path. Its GET reads `/` only and requires a bounded HTML response whose full length, setup heading and Wi-Fi form match the expected page. The new QEMU property is available only in combination with the open SoftAP peer, and the service profile is StickS3-only under the same ACL operation and mandatory capture.

The initial candidate received a guest TCP reset and reached DHCP and ARP only. The guest's WiFiManager enables AP before starting the HTTP server. A bounded retry of connections explicitly refused before the GET preserved the startup observation and allowed the confirmed response. The peer and independent reconstruction agreed on the complete body SHA-256 `155b87edfafcd2bdf6142868c48b1bdc94c8b4b6a8ac7f4576baa68bbdae7854`. The finalized pcap showed a single DORA and one bidirectional TCP payload flow. The setup frame and pre-stop ZIP were retained. After stop the virtual Flash was released and the worker had zero live leases. [WiFiManager source](https://github.com/tzapu/WiFiManager/blob/v2.0.17/WiFiManager.cpp#L685-L715)

The guest was the unchanged `firmware.bin` app SHA-256 `5c7c0b74a49cef246d11d907c87f97029c238c5f5441ab29585432120e260cd6`, placed at its normal app offset with the release's partition CSV and the pinned Arduino boot context. The composed Flash hash was `9627c7bc4a313841b5e30477030af7c68d0b76c1172b7a46072938322ba3ec70`, and the QEMU build hash was `eca4ab4bce50c10834fc92b12a3bdb69fd4c504c3281bec03574322dc6b98187`. Build from the target's pinned recipe with 0214. Register the four segments on the `sticks3` profile using normal Device Service artifacts and create an owned `qemu-wifi` session with `network.profile=sticks3-open-softap-portal` and the `network.softap.probe` grant. Read the session network receipt, save evidence before stop and check the finalized pcap and cleanup. [Repeatable source procedure](https://github.com/m5agent/m5stack-esp-emulator/blob/d627ac203218e64387355b3ea541809b4bad3157/docs/evidence/2026-11-17-sticks3-portal-page/README.md)

The same original with `sticks3-open-softap-fixture` produced 200 beacons with zero authentication, association, DORA and TCP progress. A separate ESP-IDF fixture on that profile ignored BtnB, produced application markers and fixed HTTP after BtnA, and repeated after reset and a second BtnA. Its capture had two DORAs and two bidirectional payload flows. Each run reported zero host IP backends and ended with zero active leases.

The derived summary omits local identifiers, addresses, paths and packet contents. It preserves original firmware, pcap, evidence ZIP and response hashes. Revert the source commit and use the earlier pinned runtime if reverting the new profile. Credential writes, original app STA handoff, other or protected portals, browser-WASM and physical RF remain outside the validation.
