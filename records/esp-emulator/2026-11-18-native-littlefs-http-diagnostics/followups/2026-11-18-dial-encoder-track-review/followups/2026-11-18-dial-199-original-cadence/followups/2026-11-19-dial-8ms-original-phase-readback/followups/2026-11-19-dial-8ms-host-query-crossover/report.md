# 对照原版 Dial 旋转期间的宿主查询

## 方法

相同原版 vinylM5Dial 1.0 R1F30 使用 Device Service 1.99.1 `c9ec0f27`、未加诊断的原生 QEMU 和 PORT.B 七轨 AudioPlayer。每次实验前恢复至轨 1，静候 500 ms，再用 35 ms 的 −2 格预备动作到轨 6。两种观察方式都提交同一条 +16 格输入，使用配对内相同的预备等待时间，按配对交替先后顺序。

查询组每隔约 250 ms 读取控制器交付进度，静默组在共同观察窗口前不请求进度。8 ms 组的窗口为 1.20 秒，35 ms 组为 3.0 秒。窗口后两组均用实际控制器目标、交付格数和累积边沿核对操作完成，再从新出现的 N9301 UART 指令核对第 1 轨与校验字节。

## 结果

| 间隔 | 观察方式 | 目标曲目 | 窗口结束前查询次数 |
| --- | --- | --- | --- |
| 8 ms | 查询 | 12/12 | 每次 4 |
| 8 ms | 静默 | 12/12 | 0 |
| 35 ms | 查询 | 2/2 | 每次 11 |
| 35 ms | 静默 | 2/2 | 0 |

28 次预备动作及 28 次测量动作全部通过。每次测量动作均交付 64 个 GPIO 边沿，窗口结束时已读到目标格数。保留了 240×240 非黑规整帧、同会话 ZIP 和 UART 结果。独立检查校验 ZIP CRC、清单、成员大小和摘要。停机后 Flash 释放，租约归零，隔离服务退出。

## 结论的范围

[上一轮](../../README.md)在正式运行时报告 1 次 8 ms 漏选，只读诊断轮另有 2 次，并将后两次绑定到原版轮询漏读完整相位。本轮没有漏选，因此只能记录这个配对时序下两种观察均通过，无法确定宿主查询对偶发漏选的影响。当前正式运行时没有启动逐相位取样，观察到的是控制器交付格数、边沿计数和应用 UART 结果。原固件、运行时和现有记录均保留，真机和浏览器未执行，Burner 未提交。
