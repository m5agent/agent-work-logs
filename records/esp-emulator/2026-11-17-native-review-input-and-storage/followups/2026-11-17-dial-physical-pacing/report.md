# Dial 控制器交付与延迟回调

执行 Device Service 候选 `5f6f33c63e3b685e2ee0103edf47ad7823a218ac` 和原生 Xtensa `bef8e5f1f181c341076b35ea1cb5946ba8437349ed879196469d4448e0e33e98`。用独立会话发 `kind=encoder`，同一条请求设置带符号 detent 与可选 `edge_period_ms`，等 QOM 确认目标交付后再发下一条。

- UIFlow2 官方底包加探针的原 RotaryIRQ 连续三轮各准确读到 +3@35 ms、−5@50 ms。每轮随后省略间隔的 +2 均按 5 ms 交付 8 个 GPIO 边沿，原驱动三次均读成 +1。
- ESP-IDF 公开 GPIO 中断 API 同会话九个动作捕获全部 120 个正交边沿。35 ms 边沿间隔 34400–37545 μs，50 ms 为 49543–51226 μs，默认 5 ms 为 4806–5145 μs。
- 六档速度对照中 Python 延后回调有重复的实时引脚状态，独立边沿中断仍收到不同相位。说明本次漏计发生在固件的延后采样路径。
- 旧运行时拒绝显式间隔且控制器计数未变。非法及显式空值提前拒绝。进行中的目标不能被第二条语义输入覆盖。各组实际会话取证后停止，ZIP CRC 校验通过。

保留第一次准备标记早于会话就绪的观察器失败。物理转感、真机时序、浏览器-WASM 和常驻 cutover 均为 NOT RUN。
